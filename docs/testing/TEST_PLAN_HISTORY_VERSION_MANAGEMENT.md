# Dyson Sphere Program - 履歴・バージョン管理機能 E2E テスト計画書

作成日: 2025-11-02
対象ブランチ: feature/history-version-management
対象機能: 履歴管理 / Undo-Redo / プランバージョン管理 / 差分表示

## エグゼクティブサマリ

- 履歴・バージョン管理機能のリリースに先立ち、Undo/Redo、履歴永続化、バージョン履歴、差分表示の全体的な品質を保証する。
- 主要なユーザーフロー（設定変更、ノードオーバーライド、プラン保存、発電設定）を通じた履歴記録と復元の整合性を検証する。
- 保存上限やデバウンスによる履歴集約、プランバージョンのマイグレーション、破損データからの復旧などのエッジケースを網羅する。
- 仕様の決定事項（差分形式の保存、重要操作の即時記録、トースト通知、アイコン表示など）を UI/UX 観点から確認する。

## 対象範囲と非対象

- 対象: `GlobalSettings`、`NodeOverrideSettings`、プラン保存、発電設備設定、履歴ダイアログ、プラン読み込みダイアログの新機能。
- 非対象: 計算アルゴリズム自体、UI の折りたたみ状態、お気に入り機能、既存エクスポート/インポート機能（影響範囲にないため）。

## テスト環境前提

- ブラウザ: Chromium (Playwright) を基準にクロスブラウザプロジェクトで再利用可能。
- 初期状態: 各シナリオはクリーンな localStorage と URL パラメータなしで開始。
- ローカル URL: `http://localhost:5173/` を想定（アプリ起動が必要）。
- データストア: localStorage キー `dsp-calculator-history` および `dsp-calculator-history-store` を直接検証する。

## 共通準備

1. ウェルカムモーダルが表示された場合はスキップボタンで閉じる。
2. 既存テストヘルパー `initializeApp(page)` がある場合は活用して初期化。
3. `page.evaluate` で localStorage をクリアしてから各シナリオを開始する。
4. トースト通知は data-testid `toast` (仮: 実装後に正確な値を更新) で監視する。

## テストシナリオ

### シナリオ 1: 履歴基本挙動

#### 1.1 設定変更の履歴化

- **目的**: GlobalSettings の変更が差分形式で履歴に追加されることを確認。
- **前提**: レシピ「鉄インゴット」を選択し、目標 1 で計算済み。
- **手順**:
  1. 設定パネルで増産剤を Mk.I (速度) に設定。
  2. 500ms 以上待機し、履歴ダイアログを開く。
  3. 最新の履歴エントリを選択。
- **期待結果**:
  - 履歴リストの最新行に「増産剤をmk1に変更（speed）」と表示。
  - エントリ詳細に `settings.proliferator.type = mk1` 等の差分が表示。
- **成功基準**: 履歴一覧と差分ビューの内容が仕様どおりである。
- **失敗条件**: 履歴が生成されない、説明文が仕様と異なる、差分が空。

#### 1.2 デバウンスまとめ動作

- **目的**: 500ms デバウンスにより連続操作が 1 エントリにまとまることを確認。
- **前提**: 1.1 実施後、履歴をクリア。
- **手順**:
  1. 増産剤モードを速度→追加生産→速度と 300ms 間隔で切り替える。
  2. 800ms 待機後に履歴ダイアログを開く。
- **期待結果**:
  - 履歴に 1 件のみ追加。
  - 差分内に最終状態 (速度) が保存され、中間値は記録されない。
- **成功基準**: 履歴エントリ数が 1 件、説明文が最終状態に一致。
- **失敗条件**: 複数エントリが作成される、最後の値が保存されない。

#### 1.3 Undo/Redo ボタンの有効状態

- **目的**: Undo/Redo ボタンの活性/非活性が履歴位置に応じて変化することを確認。
- **前提**: 履歴エントリが 2 件以上存在。
- **手順**:
  1. 履歴ダイアログを閉じ、トップバーの Undo ボタンを確認。
  2. Undo ボタンを 2 回押下。
  3. 再度 Undo ボタンの disabled 状態を確認。
  4. Redo ボタンを 2 回押下。
- **期待結果**:
  - 操作後に対応するトースト「増産剤設定を元に戻しました」「再適用しました」が表示。
  - 履歴インジケータ (例: 現在位置ハイライト) が移動する。
  - 履歴先頭で Undo が disabled、末尾で Redo が disabled。
- **成功基準**: ボタン状態とトースト内容が仕様と一致。
- **失敗条件**: 無効化されない、トースト未表示、履歴位置が更新されない。

#### 1.4 キーボードショートカット

- **目的**: Ctrl+Z / Ctrl+Y (Cmd 対応含む) がボタン操作と同じ挙動になることを確認。
- **前提**: 1.3 の状態から開始。
- **手順**:
  1. キーボードで Ctrl+Z を送信。
  2. Ctrl+Shift+Z (macOS のみ) または Ctrl+Y を送信。
- **期待結果**:
  - Undo/Redo に紐づくトーストが表示される。
  - ボタン状態と履歴位置が同期。
- **成功基準**: キー操作で UI 状態が正しく変化。
- **失敗条件**: キー無反応、ショートカットが重複動作する。

#### 1.5 Undo 後の履歴分岐

- **目的**: Undo 後に新しい操作を行うと Redo 履歴が破棄されることを確認。
- **前提**: currentIndex を先頭に戻した状態。
- **手順**:
  1. Undo 実行後に設定パネルでソーターを Mk.II に変更。
  2. 履歴ダイアログを開く。
- **期待結果**:
  - Redo 履歴が空。
  - 新たなエントリが最新として追加され、説明が「ソーターをmk2に変更」。
- **成功基準**: Redo ボタンが無効化される。
- **失敗条件**: Redo が残る、新操作が履歴に追加されない。

#### 1.6 履歴最大数 50 のローテーション

- **目的**: 51 件目追加時に最古エントリが削除されることを確認。
- **前提**: localStorage をクリア。
- **手順**:
  1. ループで 51 件の設定変更 (例: 目標数量を 1 ずつ増加) を実行。
  2. localStorage `dsp-calculator-history` を取得し、エントリ数を確認。
- **期待結果**:
  - エントリ数が 50。
  - 最古の timestamp が更新され、最新のみ残る。
- **成功基準**: ローテーションが正しく動作。
- **失敗条件**: 50 件を超えて保存、例外発生。

### シナリオ 2: 履歴ダイアログと差分表示

#### 2.1 差分カテゴリの色分け

- **目的**: 追加=緑、削除=赤、変更=黄で表示されることを確認。
- **手順**:
  1. 設定変更で新規プロパティを追加する操作 (例: 光子生成を有効化)。
  2. 別操作で設定を削除 (例: 光子生成を無効化)。
  3. 差分ビューで各行の色を検証。
- **期待結果**:
  - add -> 緑背景、remove -> 赤背景、change -> 黄色背景。
- **成功基準**: 3 種すべて表示確認。
- **失敗条件**: 色が期待値と異なる、表示されない。

#### 2.2 バッチ操作の説明文

- **目的**: テンプレート適用が 1 エントリとして保存され説明が分かりやすいことを確認。
- **手順**:
  1. テンプレート「終盤」を適用。
  2. 生産設備を確認し、差分が複数プロパティで表示される。
- **期待結果**:
  - 説明「テンプレート「終盤」を適用」。
  - changes 内に複数パスが含まれる。
- **成功基準**: バッチ化される。
- **失敗条件**: 個別エントリに分割される。

#### 2.3 ノードオーバーライド差分

- **目的**: affectedNodes に対象ノード ID が表示されることを確認。
- **手順**:
  1. レシピ「電磁タービン」で特定ノードにカスタム設定を適用。
  2. 履歴詳細で affectedNodes を確認。
- **期待結果**:
  - 対象ノード ID (例: `node-uuid`) が表示。
  - changes が nodeOverrides パスを指す。
- **成功基準**: ノードIDが記録される。
- **失敗条件**: null または誤った ID。

#### 2.4 Undo/Redo プレビュー (オプション機能)

- **目的**: プレビューが実装されている場合、差分がプレビューで確認できるかを確認。
- **手順**:
  1. Undo ボタンにホバーまたは長押し。
  2. プレビューが表示されるか確認。
- **期待結果**:
  - 仕様が実装されていれば差分プレビューが表示。
  - 未実装の場合は仕様に従いスキップ。
- **成功基準**: 実装状況に応じた挙動。
- **失敗条件**: 実装されているのに表示されない。

### シナリオ 3: プランバージョン管理

#### 3.1 新規プラン保存

- **目的**: プラン保存時に planId と version=1 が付与され履歴にも記録されることを確認。
- **手順**:
  1. 任意のプラン名称を入力し「保存」をクリック。
  2. 保存ダイアログでバージョン履歴を開く。
- **期待結果**:
  - バージョンリストに Version 1, 保存日時。
  - localStorage 内のプランデータに planId, version=1。
  - 履歴に type=plan エントリ、planSnapshot が存在。
- **成功基準**: planSnapshot が保存される。
- **失敗条件**: planId が空、履歴未作成。

#### 3.2 既存プランの継続保存

- **目的**: 同一プランを再保存すると version がインクリメントされることを確認。
- **手順**:
  1. 3.1 のプランを編集し再保存。
  2. バージョン履歴で Version 1 と Version 2 を比較。
- **期待結果**:
  - version が自動で +1。
  - changes 欄に差分リスト (オプション) が表示。
  - planSnapshot が最新データに更新。
- **成功基準**: Version 1 が保持され、Version 2 が追加。
- **失敗条件**: バージョンが上書き、changes 未表示 (実装されている場合)。

#### 3.3 既存プランのマイグレーション

- **目的**: planId を持たない旧データを読み込んだ際に ID が付与されることを確認。
- **手順**:
  1. localStorage に `planId` 無しのプラン JSON を注入。
  2. プラン読み込みダイアログで該当プランを開く。
  3. 再保存する。
- **期待結果**:
  - 読み込み時に planId が生成される。
  - 保存後に version=1 で登録される。
- **成功基準**: プラン破損なく読み込める。
- **失敗条件**: エラー発生、planId 未設定。

#### 3.4 バージョン復元

- **目的**: 任意のバージョンを選択して復元できることを確認。
- **手順**:
  1. バージョン履歴で Version 1 を選択し「復元」をクリック。
  2. 計算結果が Version 1 の状態に戻ることを確認。
- **期待結果**:
  - 設定パネル、Production Tree が旧状態に一致。
  - 履歴に type=plan の復元エントリが追加 (仕様要確認)。
- **成功基準**: 状態が完全に一致し再計算される。
- **失敗条件**: 差分が残る、履歴が壊れる。

#### 3.5 差分表示

- **目的**: バージョン比較で差分ツリービューが表示されることを確認。
- **手順**:
  1. Version 1 と Version 2 を選択し「差分表示」。
  2. 追加/削除/変更が正しく表示される。
- **期待結果**:
  - DiffEntry の path が正確。
  - before/after の値が読みやすい形式で表示。
- **成功基準**: UI が崩れず、色分けが仕様準拠。
- **失敗条件**: 差分なし、値が逆。

### シナリオ 4: 発電設備関連履歴

#### 4.1 テンプレート変更

- **目的**: 発電テンプレート変更が type=powerGeneration で履歴に保存されることを確認。
- **手順**:
  1. 発電設備タブでテンプレート A を選択。
  2. テンプレート B に切り替える。
  3. 履歴を確認。
- **期待結果**:
  - 説明「発電設備テンプレートをBに変更」等。
  - changes 内に templateId。
- **成功基準**: powerGeneration タイプで記録。
- **失敗条件**: settings タイプで記録されるなど誤分類。

#### 4.2 手動設備/燃料選択

- **目的**: 個別設備・燃料・増産剤設定が履歴化されることを確認。
- **手順**:
  1. 火力発電所 + 高エネルギーグラファイトを選択。
  2. 燃料を切替、増産剤を設定。
- **期待結果**:
  - changes に `power.fuel`、`power.proliferator` 等。
  - 追加で台数/燃料消費が再計算されたことを統計タブで確認。
- **成功基準**: すべてのプロパティが差分に記録。
- **失敗条件**: 一部が記録されない。

### シナリオ 5: エラーハンドリングとマイグレーション

#### 5.1 無効データ検出

- **目的**: 不正な履歴エントリが読み込まれた際にスキップされトーストで通知されることを確認。
- **手順**:
  1. localStorage に必須フィールド欠落の履歴エントリを注入。
  2. アプリをリロード。
- **期待結果**:
  - 起動時に「履歴データを読み込めませんでした」等の通知。
  - 無効エントリは表示されない。
- **成功基準**: アプリがクラッシュしない。
- **失敗条件**: 例外で停止、履歴リストに空行。

#### 5.2 バージョンマイグレーション

- **目的**: version フィールドが無い履歴エントリが最新形式に変換されることを確認。
- **手順**:
  1. 旧形式 (before/after) を含む履歴を注入。
  2. アプリをリロードし履歴ダイアログを開く。
- **期待結果**:
  - changes 形式に変換され version=最新バージョン が付与。
- **成功基準**: before/after -> changes 変換が正しい。
- **失敗条件**: 変換失敗、エントリ欠落。

#### 5.3 復元失敗時のフォールバック

- **目的**: 履歴からの復元が失敗した際に現在状態を維持しトーストで通知されることを確認。
- **手順**:
  1. 履歴エントリの changes に不正パスを含むデータを注入。
  2. Undo を実行。
- **期待結果**:
  - トーストで失敗通知。
  - 状態変更なし。
  - 問題のエントリが履歴から除外 (仕様に応じて)。
- **成功基準**: UI が正常なまま。
- **失敗条件**: アプリがクラッシュ、破損状態になる。

### シナリオ 6: 永続化と再計算

#### 6.1 再計算トリガー

- **目的**: Undo/Redo 後に再計算が自動で走り、UI が「計算中...」表示を挟むことを確認。
- **手順**:
  1. 設定を変更し履歴を作成。
  2. Undo を実行。
  3. 統計タブで再計算結果を確認。
- **期待結果**:
  - 一瞬計算中表示。
  - 設定値と計算結果が復元状態に一致。
- **成功基準**: 再計算が完了し整合性が保たれる。
- **失敗条件**: 設定値は復元されるが計算結果が古いまま。

#### 6.2 非対象状態が記録されないことの検証

- **目的**: UI 折りたたみ状態やお気に入りが履歴に含まれないことを確認。
- **手順**:
  1. Production Tree を展開/折りたたみ。
  2. お気に入り登録。
  3. 履歴ダイアログを確認。
- **期待結果**:
  - 履歴リストに該当操作が存在しない。
- **成功基準**: 非対象項目が記録されない。
- **失敗条件**: UI 状態が履歴として表示。

#### 6.3 localStorage 永続化

- **目的**: リロード後も履歴スタックと現在位置が復元されることを確認。
- **手順**:
  1. 複数の履歴エントリを作成し Undo を 1 回実行。
  2. ページをリロード。
- **期待結果**:
  - currentIndex が Undo 後の位置を保持。
  - Undo/Redo ボタン状態が継続。
- **成功基準**: 永続化が正しく機能。
- **失敗条件**: currentIndex がリセット、履歴が消失。

### シナリオ 7: UI/UX 仕様確認

#### 7.1 履歴エントリアイコン

- **目的**: タイプごとのアイコン (⚙️, 🎯, 📋, ⚡) が表示されることを確認。
- **手順**:
  1. 各タイプの履歴エントリを少なくとも 1 件ずつ作成。
  2. 履歴リストを確認。
- **期待結果**:
  - タイプに応じたアイコンが表示。
- **成功基準**: すべての種類で正しいアイコン。
- **失敗条件**: アイコン欠落、誤表示。

#### 7.2 トースト通知のタイムアウト

- **目的**: Undo/Redo 通知が 3 秒で自動消去されることを確認。
- **手順**:
  1. Undo を実行。
  2. トーストが 3 秒後に消えるまで待機。
- **期待結果**:
  - 3 秒前後で自動クローズ。
- **成功基準**: 3 秒付近で消える。
- **失敗条件**: 消えない、即座に消える。

## リスクとオープンポイント

- 差分 UI の data-testid は未定のため実装後に更新が必要。
- 仕様でオプション扱いとなっている Undo/Redo プレビューの有無を確認し、未実装の場合はスコープ外とする。
- 大量履歴のパフォーマンス測定は手動検証が困難なため、メトリクス収集が可能か開発チームと要調整。

## 推奨次ステップ

1. Playwright 用共通ヘルパーに履歴ダイアログ操作メソッドを追加し、シナリオを自動化しやすくする。
2. localStorage 注入/検証ユーティリティを整備し、マイグレーション系テストの冪等性を確保する。
3. 差分 UI の data-testid/role を事前に確定し、テストのセレクタ安定性を高める。
